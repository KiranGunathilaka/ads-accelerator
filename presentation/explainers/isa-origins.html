Where the ISA came from, and why every instruction is there

Which of the 32 instructions came from v1.0 or the reference paper and which are new, one card per instruction with its justification and precedent, an honest look at the 12 the program never runs, and the reasoning behind every design parameter.

The short answer

The 32 instructions are not all new, and they were not copied from one source.

Rakindu's v1.0 draft defined the 32-bit format, the four groups and all 32 opcode slots for Block-LMS. It took the overall architecture from Mahmood & Al-Jbaar (2011): one control unit broadcasting to lanes that each have their own registers and memory, a lane-enable mask, and category bits for a fast pre-decode. v1.1 kept 28 of v1.0's 32 slots (18 unchanged in name and role, 6 renamed, 4 reworked), dropped 4, and added 4 new ones: WLD, SST, SLD and PKCLR.

Each instruction on its own has a precedent in a well-known machine: the CRAY-1 and MMX from the course lecture, ARM NEON, RISC-V V, and DSPs such as the TI C54x and ADI Blackfin. What is specific to this design is which instructions were chosen, and the four ideas built for this algorithm: the sliding-window register, the reversed weights, the circular input rings and the peak detector.

20 of the 32 run in every block. The other 12 are listed below with an honest verdict.

Lineage: paper → v1.0 → v1.1

Mahmood & Al-Jbaar, 2011

“Design and implementation of SIMD Vector Processor on FPGA”, IEEE ISIICT 2011. According to its abstract: 4 parallel lanes (processing elements) working at the same time, each with its own arithmetic units, vector register file and local memory, plus a scalar processor for the instructions the lanes can't run.

Gave us: the organisation. One instruction stream, identical lanes, per-lane memory.

v1.0 · Rakindu

Mapped Block-LMS onto that organisation: 5 phases, 16-lane vectors, 3 PEs (one per mic pair).

  • 32-bit format, 5-bit opcode, 5-bit register fields, 12-bit immediate
  • 4 groups of 8 via the top two opcode bits (the paper's pre-decode)
  • all 32 slots and mnemonics
  • CSRs including MASK_WORK and MASK_NET (the paper's Mask_Work_Reg / Mask_Net_Reg)

v1.1 · Kiran

Checked v1.0 against the golden model and made it executable (16 fixes; see the changelog):

  • address registers, post-increment, circular rings
  • sliding-window register (WLD, WSLIDE)
  • a real zero-overhead LOOP
  • fixed-point semantics (shifts, rounding, saturation)
  • verified: 78-instruction program bit-exact with the fixed-point model

Every instruction, justified

Each card answers the same five questions. Why it exists: which step of the algorithm needs it and how often it runs. Why this form: what changed from v1.0 and why the fields are what they are. Seen before in: known machines with the same idea (named so you can say it is an established technique, not because we copied them). Hardware: what it costs. Without it: what would happen if we removed it.

Group 00 · Vector arithmetic

VMAC

00000Kept from v1.0runs every block · 12 in program · 1 024× per block

In plain words: multiply 16 pairs of numbers and add each product to that lane's running sum.

VACC[i] = (.C ? 0 : VACC[i]) + SRC1[i] × (SRC2[i] >> sh)

Why it exists
Phases 1 and 3 are two matrix–vector products: 16 384 of the 16 576 operations per filter per block. One VMAC does 16 multiply-adds per PE, 48 across the cluster. It is 1 024 of the 1 709 instructions executed per block (60 %).
Why this form
Three changes from v1.0, which did V_DST += SRC1 × SRC2. (1) The accumulator is VACC, the 48-bit P register inside each DSP48E1, not a 32-bit vector register. A product is up to 41 bits and a row adds 64 of them (47 bits), so a 32-bit register would overflow. Accumulating inside P also avoids a register-file write every cycle. (2) The .C flag (IMM[0]) starts a new sum by selecting DSP OPMODE Z = 0. It replaces v1.0's per-row SACC_CLR V2, a scalar instruction that v1.0 applied to a vector register. (3) sh (IMM[4:1]) shifts SRC2 right before the multiply so a 32-bit Q2.30 weight fits the 25-bit A port (sh = 7). SRC1 can also name a window chunk W0–W7 (operand codes 8–15), so the sliding window feeds the multipliers without being copied into vector registers first.
Seen before in
The multiply-accumulate is the defining DSP instruction: MMX PMADDWD (lecture 29a, MMX slides), NEON VMLA/VMLAL, RISC-V V vmacc. TI C55x (40-bit AC0–AC3) and ADI Blackfin (40-bit A0/A1) also have wide dedicated accumulators.
Hardware
16 DSP48E1 per PE. Window sample → B port (18 bit); weight or error → A port (25 bit); P (48 bit) = VACC. Consecutive VMACs accumulate through the DSP's internal P feedback, so they issue every cycle.
Without it
Each chunk would need VMUL + VADD: twice the instructions in the two hot loops, with sums held in 32-bit registers that overflow.

VSUB

00001Renamed from v1.0 (VSUB_V)runs every block · 1 in program · 8× per block

In plain words: subtract two vectors, lane by lane.

Vd[i] = sat(Va[i] − Vb[i]) (IMM[0]: clamp to 16 bits, else 32)

Why it exists
Phase 2 computes the error e = d_delayed − y, 16 samples at a time: 8 per block.
Why this form
Renamed from VSUB_V. All four element-wise vector ops lost the _V suffix, because every vector op works element by element unless its name says otherwise (VREDUCE, VSCALE). Saturation is new. When the filter is far off, d − y can exceed the Q1.15 range. Clamping keeps e at the right sign; wrapping would flip it and push the weights the wrong way. The fixed-point model clamps the same way, which is part of why the ISA run matches it bit for bit.
Seen before in
MMX PSUBSW, NEON VQSUB, RISC-V V vssub (all saturating).
Hardware
Vector ALU: 16 × 32-bit subtract with clamp.
Without it
VADD plus a negate instruction. Nothing cheaper forms e.

VADD

00010Renamed from v1.0 (VADD_V)runs every block · 1 in program · 4× per block

In plain words: add two vectors, lane by lane.

Vd[i] = sat(Va[i] + Vb[i])

Why it exists
Phase 4 applies the update w_rev += Δw: 4 per block (64 weights / 16 lanes).
Why this form
Renamed from VADD_V. It uses 32-bit saturation, so a weight that grows past ±2 in Q2.30 stops at the limit instead of wrapping to the opposite sign.
Seen before in
MMX PADDSW, NEON VQADD, RISC-V V vsadd.
Hardware
Same vector ALU as VSUB.
Without it
The weight update could not be applied.

VSCALE

00011Kept from v1.0runs every block · 1 in program · 4× per block

In plain words: multiply every lane by one scalar (used for μ).

Vd[i] = sat(((Va[i] >> pre) × Ss) >> post)

Why it exists
Phase 4 computes Δw = μ · g, with the scalar μ sent to all 16 lanes: 4 per block.
Why this form
Kept from v1.0 (V_DST = SRC1 × S_src). v1.1 adds two shifts because the operands are fixed-point. pre = 7 turns the Q2.30 gradient into 25 bits for the A port. The product with Q1.15 μ has 38 fractional bits, and post = 8 brings it back to Q2.30. Separate instructions would need three steps (shift, multiply, shift). VSCALE reads the scalar register directly, so no broadcast (splat) is needed first.
Seen before in
NEON multiply by scalar (VMUL by element) and VQDMULH (Q15 fractional multiply); RISC-V V vmul.vx.
Hardware
Reuses the 16 DSP48E1 lanes (μ on the B port); the product goes back to the vector register file.
Without it
VMOV splat, VMUL and shifts: 3–4 instructions per chunk instead of 1.

VABS

00100Kept from v1.0weak case (not run)

In plain words: absolute value of every lane.

Vd[i] = |Va[i]|

Why it exists
The v1.1 program never runs it. In v1.0 it fed the peak search (VABS V7, V6, then PKMAX V7). In v1.1, PKMAX takes the absolute value inside its comparator tree, which saves 4 instructions and a register per block.
Why this form
Unchanged from v1.0.
Seen before in
NEON VABS/VQABS, SSSE3 PABSW.
Hardware
16 negate-and-select circuits in the vector ALU (small).
Without it
Nothing changes in the current program. The case for it is weak: a possible use is a mean |e| convergence monitor. It is the first candidate if a slot is needed for something new.

VMOV

00101Renamed from v1.0 (VMOV_V)utility / debug (not run)

In plain words: copy a vector, or fill all 16 lanes with one scalar.

Vd = Va, or Vd[i] = Ss for every lane (splat) if IMM[0]

Why it exists
Not used per block. It is the only instruction that puts a scalar into every lane, for example an all-zero vector (splat of the ZERO code) to clear w_rev in a reset program. It is also the register copy that a software-pipelined loop would need.
Why this form
Renamed from VMOV_V. The splat mode replaces v1.0's VLD_S (load one word and broadcast), which v1.1 does as SLD + VMOV. That freed a memory-group slot for the new window and scalar memory instructions.
Seen before in
NEON VMOV/VDUP, RISC-V V vmv.v.v/vmv.v.x.
Hardware
A multiplexer in front of the vector register write port.
Without it
No way to build a constant vector. The per-block program would not change.

VREDUCE

00110Kept from v1.0runs every block · 2 in program · 192× per block

In plain words: add the 16 running sums together into one number.

Sd = sat((Σ_i VACC[i] + round) >> sh)

Why it exists
Each output y[i] (128 per block) and each gradient g[k] (64 per block) ends as 16 lane partial sums that must become one number: 192 per block.
Why this form
Kept from v1.0 (S_DST = Σ V_SRC[i]). v1.1 sums VACC directly instead of a V register, so the 48-bit partial sums never pass through 32-bit registers. It also rescales in the same instruction: IMM[4:0] = shift, IMM[5] = round, IMM[6] = clamp to 16 bits. Phase 1 uses sh = 23 (38 fractional bits → 15, rounded, clamped: y in Q1.15). Phase 3 uses sh = 7 = log2 B, which turns the sum into the mean. That shift is the ÷B in μ/B, so the division costs nothing. The result is ready 5 cycles after issue (4 tree stages + round/clamp).
Seen before in
RISC-V V vredsum.vs, AArch64 NEON ADDV. x86 SSE needs several PHADD/shuffle steps for the same thing.
Hardware
15 adders in 4 pipelined stages, about 52 bits wide (16 inputs of 48 bits), then a shifter, rounder and saturator.
Without it
15 scalar additions per output, more instructions per row than the whole 7-instruction loop.

VMUL

00111Renamed from v1.0 (VMUL_V)weak case (not run)

In plain words: multiply two vectors, lane by lane.

Vd[i] = sat((Va[i] × Vb[i]) >> sh)

Why it exists
Not used. Block-LMS never needs an element-wise product kept in a register: every product either feeds a sum (VMAC) or multiplies by a scalar (VSCALE). The NLMS power Σx² is also a VMAC.
Why this form
Renamed from VMUL_V; the shift was added for fixed point.
Seen before in
NEON VMUL, RISC-V V vmul.vv, SSE PMULLW.
Hardware
Almost nothing extra: the path from the DSPs back into the vector registers already exists for VSCALE. VMUL feeds a vector instead of the broadcast scalar.
Without it
Nothing changes for this algorithm. It stays as a general-purpose operation that costs only decode.

Group 01 · Memory / AGU

VLD

01000Kept from v1.0runs every block · 17 in program · 40× per block

In plain words: load 16 words from memory into a vector register.

Vd = M[An … An+15]; An += sext(imm) (An must be 16-aligned)

Why it exists
Loads w_rev (Phases 1, 4, 5), e (Phase 3), d and y (Phase 2) and g (Phase 4) into registers: 40 per block.
Why this form
Kept from v1.0 with two fixes. (1) It names an address register An. v1.0's VLD had no pointer field, yet its listings used seven pointers (x_ptr, w_ptr, d_ptr, …). Three AGU_SETs in a row would have overwritten each other. (2) Post-increment by IMM12 replaces v1.0's separate AGU_INC after every access; v1.0's Phase 2 loop spent 3 of its 8 instructions on AGU_INC. Vector accesses must be 16-aligned, so a load is one row across the 16 banks in one cycle and needs no rotator.
Seen before in
Auto-increment addressing LD R4 = MEM[R1++] (lecture 29a, scalar code example); NEON VLD1 {…}, [Rn]!; RISC-V V vle32.v (unit stride). The 16 word-interleaved banks are the lecture's vector memory system (CRAY-1: 16 banks).
Hardware
16 BRAM18 read ports into the vector register file; result ready after 2 cycles.
Without it
No way to get data into the vector registers.

VST

01001Kept from v1.0runs every block · 2 in program · 12× per block

In plain words: store a vector register to memory.

M[An … An+15] = Vs; An += sext(imm)

Why it exists
Stores e (Phase 2, 8 times) and the updated w_rev (Phase 4, 4 times): 12 per block.
Why this form
Same fixes as VLD: a named pointer, post-increment, aligned only.
Seen before in
As for VLD.
Hardware
16 BRAM18 write ports; the PE has priority over the input writer on these ports.
Without it
Results could not go back to memory.

AGU_SET

01010Kept from v1.0runs every block · 13 in program · 13× per block

In plain words: point an address register at a place in memory.

An = (Am or ZERO) + imm; circular flag = SRC2[0]

Why it exists
Points an address register at a region at the start of each phase: 13 per block.
Why this form
Kept by name. v1.0's AGU_SET loaded its one implicit pointer with IMM12. v1.1 names the destination An and adds a base register Am and a circular flag. The base register is what makes the rings work: AGU_SET A0, A7, X_RING, circ=1 points A0 at x_full[1] of the current block (A7 holds the block base) with no scalar arithmetic. The flag makes later post-increments wrap inside the 512-word ring.
Seen before in
The CRAY-1 has 8 address registers (lecture 29a, CRAY-1 slide). The TI C54x has AR0–AR7, with BK setting the circular-buffer size. ADI SHARC/Blackfin address generators have index, base and length registers.
Hardware
Shared AGU: 8 × 13-bit registers, 8 circular flags, one adder.
Without it
Pointers could only be constants. The block position in the ring would have to be computed in scalar registers and then moved into the AGU.

AGU_ADD

01011Reworked from v1.0 (AGU_INC)runs every block · 1 in program · 1× per block

In plain words: move an address register along.

An += sext(imm) (wraps inside the ring if An is circular)

Why it exists
Moves the block base A7 on by B at the end of every block: 1 per block.
Why this form
v1.0's AGU_INC added a fixed 16 to its single pointer after every access. v1.1 moves that per-access case into post-increment and keeps one general add for everything else. AGU_SET cannot do this job because it does not wrap: A7 would leave the X ring and point into the D ring after four blocks.
Seen before in
The address-generator 'modify' step (I += M, with circular wrap) on ADI SHARC/Blackfin; TI C54x MAR.
Hardware
The same adder as post-increment.
Without it
A7 could not advance modulo 512.

WLD

01100New in v1.1runs every block · 12 in program · 12× per block

In plain words: load 16 samples into one chunk of the window register.

window chunk Wc = low 16 bits of M[An … An+15]; An += imm

Why it exists
Fills the sliding-window register at the start of Phase 1 (4 chunks) and Phase 3 (8 chunks): 12 per block.
Why this form
New in v1.1, together with WSLIDE. v1.0 loaded each row of X with four VLDs starting at x_ptr + i: an arbitrary word offset. Sixteen single-port banks can deliver an aligned row in one cycle, but not an unaligned one, unless every PE gets a rotator or crossbar. WLD loads only aligned chunks, once per phase. It keeps the low 16 bits because samples are Q1.15, which halves the window's flip-flops.
Seen before in
Loading a delay line (see WSLIDE).
Hardware
The same bank read as VLD, written into window chunk c instead of a vector register.
Without it
The window could not be filled.

WSLIDE

01101Reworked from v1.0 (AGU_SLIDE)runs every block · 2 in program · 192× per block

In plain words: shift the window by one sample and read the one new sample.

WIN[0 … n−2] = WIN[1 … n−1]; WIN[n−1] = M[An]; An += 1 (n = len)

Why it exists
Row i+1 of X is row i moved by one sample plus one new sample, and so is column k+1. WSLIDE makes that step with a single one-word read: 128 times in Phase 1, 64 times in Phase 3.
Why this form
Replaces v1.0's AGU_SLIDE, which only moved a pointer by one sample, so every row still needed four unaligned 16-wide loads. Moving the data instead of the pointer keeps every memory access either aligned or a single word. len (IMM) sets the window length: 64 for rows (L), 128 for columns (B). v1.0's AGU_COL is gone because, with w stored reversed, columns slide the same way as rows.
Seen before in
RISC-V V vslide1down.vx does exactly this (every element moves down one place and a scalar enters at the top); here the new value comes straight from memory. DSPs keep FIR delay lines the same way, e.g. TI C54x MACD, a MAC that also shifts the delay line. NEON VEXT extracts a window from two registers.
Hardware
128 × 16-bit shift register (2 048 flip-flops), one single-bank read, and an 8:1 chunk multiplexer in front of the DSP B ports.
Without it
4 (Phase 1) or 8 (Phase 3) unaligned loads per row or column. That needs a 16 × 16 word rotator per PE, the most LUT-hungry structure a PE could have.

SST

01110New in v1.1runs every block · 2 in program · 192× per block

In plain words: store one scalar to memory.

M[An] = Ss; An += imm

Why it exists
Writes each y[i] and g[k] as soon as VREDUCE produces it: 192 per block.
Why this form
New in v1.1. v1.0's listings used VST_S for this, but VST_S was not in the opcode table. SST uses one bank's write enable, so it writes one word without touching the other 15 banks.
Seen before in
The scalar store of any load/store ISA. The CRAY-1 pairs its vector registers with scalar registers the same way.
Hardware
Bank select from address bits [3:0] plus that bank's write enable.
Without it
Results would have to be packed into a vector register first (a lane-insert instruction) and stored 16 at a time.

SLD

01111New in v1.1utility / debug (not run)

In plain words: load one word into a scalar register.

Sd = M[An]; An += imm

Why it exists
Not used per block. It is the load partner of SST, and SLD + VMOV splat replaces v1.0's VLD_S (load one word and broadcast it). Uses: reading a constant kept in memory, or reading the weights around the peak if sub-sample interpolation ever moves onto the accelerator.
Why this form
Same addressing as SST.
Seen before in
The scalar load of any ISA.
Hardware
Almost nothing extra: WSLIDE already needs a one-word read path (16:1 bank multiplexer); SLD sends the word to a scalar register instead of the window.
Without it
The per-block program would not change.

Group 10 · Scalar / loop

SMUL

10000Kept from v1.0weak case (not run)

In plain words: multiply two scalars.

Sd = Sa × Sb

Why it exists
Not used. v1.0 listed it for computing μ/B, which v1.1 does with the VREDUCE shift. The NLMS path doesn't need it either: with L = 64 and a 128-sample power window, L·Pₓ = Σx² / 2, which is a shift.
Why this form
Unchanged.
Seen before in
RISC-V M mul.
Hardware
One DSP48E1 per PE: 3 of the 51 DSPs in the resource estimate.
Without it
Removing it saves 3 DSP48E1 (51 → 48). This is the only unused instruction with a real hardware cost, so decide on it before writing RTL.

SADD

10001Kept from v1.0for block-NLMS (not run yet)

In plain words: add two scalars (plus a constant).

Sd = Sa + Sb + sext(imm)

Why it exists
Not used by the μ/B program. Block-NLMS needs it once per block to add ε to the power (L·Pₓ + ε) before dividing. It is also the general scalar add.
Why this form
v1.1 adds the immediate, so a constant can be added without a separate SIMM. With the ZERO operand it also covers SMOV (Sd = Sa + ZERO) and SIMM (Sd = ZERO + ZERO + imm).
Seen before in
RISC-V add / addi.
Hardware
One 32-bit adder per PE.
Without it
NLMS could not add ε.

SSUB

10010Kept from v1.0weak case (not run)

In plain words: subtract two scalars (plus a constant).

Sd = Sa − Sb + sext(imm)

Why it exists
Not used. v1.0 used it for τ = center_tap − peak_idx. PKOUT now does that in one step (v1.0 actually subtracted twice).
Why this form
Unchanged apart from the immediate.
Seen before in
RISC-V sub.
Hardware
Shares SADD's adder (one inverted input).
Without it
Nothing changes. It is kept for completeness and costs only decode.

SDIV

10011Kept from v1.0for block-NLMS (not run yet)

In plain words: divide two scalars (slow: 34 cycles, once per block).

Sd = (Sa << imm) / Sb (iterative, 34 cycles)

Why it exists
Not used by the μ/B program. It is the NLMS step size μ_eff = μ / (L·Pₓ + ε), computed once per block. In the tracking study block-NLMS was the best update (88.0 % within ±1 sample at μ = 0.64, against 85.6 % for μ/B at μ = 0.5), and its step does not depend on how loud the input is.
Why this form
v1.0 used SDIV to compute μ/B. That is now the VREDUCE shift, so SDIV's only job is NLMS. The pre-shift (IMM) keeps precision in the fixed-point quotient. It is iterative because one 34-cycle division per block is about 0.01 % of the 266 700-cycle block period, and a fast divider would cost DSPs or many LUTs.
Seen before in
RISC-V M div, which is multi-cycle in most small cores.
Hardware
Shift-and-subtract divider in LUTs, one per PE.
Without it
NLMS would have to move to the ARM: it could compute μ_eff from the audio it sends and write it to the MU CSR every block. That is a valid fallback.

SMOV

10100Kept from v1.0weak case (not run)

In plain words: copy a scalar.

Sd = Sa

Why it exists
Not used. It does the same as SADD Sd, Sa, ZERO.
Why this form
Unchanged. Redundant, but it makes assembly easier to read.
Seen before in
RISC-V mv is only a pseudo-instruction for addi rd, rs, 0, the same situation.
Hardware
Decode only.
Without it
Nothing. It could become an assembler alias and free its slot.

Sd = sext(imm)

Why it exists
Not used. It does the same as SADD Sd, ZERO, ZERO, imm. v1.0 needed it to clear the scalar accumulator and the peak registers; VMAC.C and PKCLR do those jobs now.
Why this form
Unchanged.
Seen before in
RISC-V li (a pseudo-instruction built from addi/lui).
Hardware

Without it

CSR_RD

10110Reworked from v1.0 (VLD_CSR)runs every block · 1 in program · 1× per block

In plain words: read a setting the ARM wrote (e.g. μ).

Sd = CSR[imm]

Why it exists
Reads μ into S0 at the start of every block. Because μ is read every block, the ARM can change it while the cluster runs, without reloading the program. The CSRs are the only way ARM settings reach the datapath; the ARM cannot write the PE memories.
Why this form
v1.0's VLD_CSR sat in the vector-memory group although it reads no memory, so v1.1 moved it to the scalar group, where its result goes. The CSR index now sits in IMM12[3:0]. v1.0 put it in a register field behind a 2-bit type tag, and the CSR tag overlapped index bit 3, so only 8 of the 16 CSRs could be reached.
Seen before in
RISC-V Zicsr csrr (csrrs rd, csr, x0).
Hardware
16:1 multiplexer from the CSR bank to the scalar write port.
Without it
μ would have to be a constant inside the program.

LOOP

10111Reworked from v1.0 (LOOP_SET)runs every block · 5 in program · 5× per block

In plain words: repeat the next few instructions a given number of times.

repeat the next len instructions count times (len = DST field, 1–31; count = IMM12, up to 4 095)

Why it exists
All control flow in Block-LMS is counted loops. Five LOOPs turn the 78 stored instructions into the 1 709 executed per block. Fully unrolled, the program would be about 1 700 instructions, more than three times the 512-word instruction memory.
Why this form
v1.0 had LOOP_SET to load a counter, and every listing ended its loops with LOOP_DEC → label. LOOP_DEC was not defined, and all 32 slots were already taken. v1.1 uses one instruction that records start, end and count. The fetch unit compares the PC with the loop end and jumps back in the same cycle, so iterations cost nothing. A decrement-and-branch would add at least one instruction to each of the 208 loop iterations per block, plus any branch bubble. The loop stack is 2 deep. The current program needs only 1 level, because the inner chunk loops are unrolled; the second level is for B or L above 128, where they can't be.
Seen before in
Zero-overhead loops are standard in DSPs: ADI Blackfin LSETUP with two loop units (LC0/LC1), Qualcomm Hexagon loop0/loop1, ADI SHARC DO … UNTIL, TI C54x RPTB. The lecture's scalar example uses DECBNZ (decrement and branch) and lists 'fewer branches' as a vector-processor advantage.
Hardware
Loop stack of 2 × {start, end, count} and one comparator on the PC.
Without it
Either an instruction memory 4× larger, or a branch instruction plus its penalty.

Group 11 · Control / result

PKMAX

11000Kept from v1.0runs every block · 1 in program · 4× per block

In plain words: compare 16 weights with the largest seen so far; remember the biggest and its position.

compare |Va[i]| over 16 lanes in a tree, then against the running max; keep the winner's index

Why it exists
τ comes from argmax |w_rev| over 64 weights: 4 per block.
Why this form
Kept from v1.0 with two changes. It takes the absolute value itself (v1.0 needed VABS first). It also keeps its own index counter (+16 per call), so software does not track positions. Ties: inside the tree the lower lane wins, and the running compare is a strict >, so the earliest index wins, exactly like numpy.argmax. That is why τ matches the golden model bit for bit.
Seen before in
SSE4.1 PHMINPOSUW returns the minimum of 8 words and its position; ADI Blackfin SEARCH finds a maximum or minimum and where it is; RISC-V V vredmax returns only the value.
Hardware
16-input comparator tree (4 stages) plus a running max/index register per PE; 5-cycle latency.
Without it
64 single-word loads per PE, each with a compare and a conditional update. This ISA has no branches, so that would also need a conditional-select instruction.

PKOUT

11001Renamed from v1.0 (PKIDX_OUT)runs every block · 1 in program · 1× per block

In plain words: turn the peak position into τ and write it where the ARM can read it.

CSR[TAU_pe] = peak_idx − imm

Why it exists
Writes the finished τ into this PE's result register (TAU21, TAU31 or TAU41): once per block.
Why this form
Renamed from PKIDX_OUT. It now subtracts an immediate: with reversed weights, τ = k* − (L−1−L/2), so imm = 31. v1.0 computed center_tap − index twice (SSUB, then PKIDX_OUT). PKOUT is also the only instruction in which each PE writes its own CSR. CSR_WR writes one shared CSR, so it could not return three different τ values.
Seen before in
Specific to this application; there is no general-purpose equivalent.
Hardware
A subtractor and a per-PE CSR write.
Without it
The three τ values could not reach the ARM.

SYNC

11010Kept from v1.0runs every block · 1 in program · 1× per block

In plain words: wait until a full new block of samples has arrived.

SYNC 0: memory fence · SYNC 1: stall until the input writer has a full new block

Why it exists
SYNC 1 at PC 0 makes each pass wait for its block of audio: 1 per block.
Why this form
v1.0 defined SYNC only as a pipeline fence. v1.1 adds mode 1 (wait until SAMPLES_IN ≥ (blocks_done + 1)·B), which lets the cluster run by itself: HALT (with AUTO) → PC 0 → SYNC 1 waits for the next block. This program doesn't need mode 0: single issue plus the scoreboard already keeps memory accesses in order.
Seen before in
Mode 0: RISC-V FENCE, ARM DMB. Mode 1 is like ARM WFE (wait for event), where the event is 'block ready'.
Hardware
A comparator between SAMPLES_IN and the block counter that holds issue.
Without it
The ARM would have to write START for every block (375 times a second), and the cluster would depend on the ARM's interrupt latency.

PKCLR

11011New in v1.1runs every block · 1 in program · 1× per block

In plain words: reset the peak search.

peak max = −1, index = 0, counter = 0

Why it exists
Resets the peak detector before each block's search.
Why this form
New, in the slot of v1.0's PHASE_END. v1.0 reset 'peak_val' and 'peak_idx' with SIMM S2, 0 and SIMM S3, 0. But PKMAX keeps its running max inside the peak detector, not in S2/S3, so those two instructions reset nothing that PKMAX uses. The max starts at −1 so the first compare always wins, even when every weight is 0.
Seen before in
Specific to this application (the peak detector is ours).
Hardware
Synchronous reset of three registers.
Without it
The previous block's peak would carry over into the next search.

IRQ

11100Renamed from v1.0 (IRQ_FIRE)runs every block · 1 in program · 1× per block

In plain words: tell the ARM the results are ready.

STATUS.DONE = 1; raise IRQ_F2P if CTRL.IRQ_EN

Why it exists
Tells the ARM that TAU21/31/41 are ready: once per block.
Why this form
Renamed from IRQ_FIRE. The way it is cleared changed. v1.0 cleared it with CTRL.RESET, but in v1.1 a reset also clears the ring position (A7) and the sample counter. The ARM now clears the interrupt by writing 1 to STATUS.DONE, which touches nothing else.
Seen before in
Write-1-to-clear status bits are the usual pattern in AXI peripherals, including the Xilinx AXI DMA status register.
Hardware
One flag and a level interrupt output to the Zynq's IRQ_F2P.
Without it
The ARM would have to poll STATUS.

NOP

11101Kept from v1.0weak case (not run)

In plain words: do nothing for one cycle.

no operation

Why it exists
Not used. The scoreboard inserts stall cycles automatically, so the program never needs NOPs to wait for a result.
Why this form
Unchanged. It costs nothing, and it gives a harmless word for overwriting an instruction when patching the instruction memory by hand.
Seen before in
Every ISA has one. In statically scheduled designs (no hardware interlocks) NOPs fill latency slots; that is the design we did not choose.
Hardware
Decode only.
Without it
Nothing.

HALT

11110Kept from v1.0runs every block · 1 in program · 1× per block

In plain words: stop; restart automatically when the next block arrives.

PC ← 0; wait for CTRL.START, or restart at once if CTRL.AUTO

Why it exists
Ends each block's pass: 1 per block.
Why this form
Kept from v1.0 ('await next DMA/START'). v1.1 adds the AUTO restart. With SYNC 1 at PC 0, the cluster then processes block after block without any action from the ARM.
Seen before in
x86 HLT; RISC-V WFI plays a similar role.
Hardware
Sequencer state.
Without it
The program would have no defined end.

CSR_WR

11111Kept from v1.0utility / debug (not run)

In plain words: write a value where the ARM can read it.

CSR[imm] = Ss

Why it exists
Not used per block. It lets the program report a value to the ARM. That covers the debug purpose of v1.0's PHASE_END (write the phase number). Later it could report signal power, so the ARM knows when to hold the estimate (ISA_Design.md §14).
Why this form
Kept from v1.0. The CSR index moved into IMM12, the same fix as CSR_RD. It writes one shared CSR (the simulator takes PE0's value).
Seen before in
RISC-V Zicsr csrw.
Hardware
A write port from the scalar registers into the CSR bank.
Without it
The per-block program would not change; only debug visibility would be lost.

The 12 instructions the program never runs

The verified per-block program uses 20 opcodes. The other 12 come from v1.0, or are the obvious partner of an instruction that is used. Here is the honest status of each:

InstructionStatusIf removed
VABSweak case (not run)Nothing changes in the current program. The case for it is weak: a possible use is a mean |e| convergence monitor. It is the first candidate if a slot is needed for something new.
VMOVutility / debug (not run)No way to build a constant vector. The per-block program would not change.
VMULweak case (not run)Nothing changes for this algorithm. It stays as a general-purpose operation that costs only decode.
SLDutility / debug (not run)The per-block program would not change.
SMULweak case (not run)Removing it saves 3 DSP48E1 (51 → 48). This is the only unused instruction with a real hardware cost, so decide on it before writing RTL.
SADDfor block-NLMS (not run yet)NLMS could not add ε.
SSUBweak case (not run)Nothing changes. It is kept for completeness and costs only decode.
SDIVfor block-NLMS (not run yet)NLMS would have to move to the ARM: it could compute μ_eff from the audio it sends and write it to the MU CSR every block. That is a valid fallback.
SMOVweak case (not run)Nothing. It could become an assembler alias and free its slot.
SIMMweak case (not run)Nothing. It could become an assembler alias.
NOPweak case (not run)Nothing.
CSR_WRutility / debug (not run)The per-block program would not change; only debug visibility would be lost.

How to say it. “20 instructions carry the algorithm. SDIV and SADD are there for block-NLMS, which simulated best. VMOV, SLD and CSR_WR are utility and debug. The remaining seven came from v1.0 and cost only decode, except SMUL, which costs 3 DSP slices and is on our list to decide before RTL. Twenty needed instructions already require a 5-bit opcode, so the spare codes are free.”

What NLMS would add (sketch, not yet simulated)

; once per block, after Phase 1 while V0–V3 are free   (Open item 2 in ISA_Design.md)
AGU_SET A0, A7, X_RING, circ=1
VLD     V0, [A0]+16          ; first aligned chunk of x_full[1..128]
VMAC.C  V0, V0               ; VACC  = x²
LOOP    7, 2
  VLD     V0, [A0]+16        ; the other 7 chunks
  VMAC    V0, V0             ; VACC += x²
VREDUCE S2, sh=…             ; L·Pₓ = 64 · Σx² / 128 = Σx² / 2: a shift, folded into sh
                             ; (sh must also bring Σx², up to 39 bits, into a 32-bit register)
SADD    S2, S2, ZERO, imm=ε  ; + ε, so silence can't divide by zero
SDIV    S3, S0, S2, pre=…    ; S3 = μ / (L·Pₓ + ε)
; Phase 4 then uses S3 instead of S0 in VSCALE

That is about 20 extra instructions and one 34-cycle division per block, small next to the 2 695-cycle block. Two details for the scaling study: the tracking study averaged the power over the 191 samples x_full[1…191], while this sketch uses the 128 aligned samples x_full[1…128]; and the shift and pre values still have to be chosen so the quotient keeps its precision. The same step size can also freeze the filter in silence without a branch: if the power is below a threshold, the ARM (or the program) makes μ zero.

Every design parameter, and why

ChoiceValueWhyAlternative we rejected
Instruction width32 bits, one fixed formatOne instruction per cycle from one BRAM18 (512 × 36). Every field sits at a fixed bit position, so decoding is wiring and takes one cycle.16-bit instructions can't hold three register fields and a 12-bit immediate. VLIW would widen the instruction memory and need a scheduler, and would gain nothing: one VMAC per cycle already keeps all 48 DSPs busy.
Opcode5 bits → 32 codes20 instructions run every block, so 4 bits (16 codes) is too few. 5 bits is the minimum and leaves 12 codes for NLMS, utility and spare.More bits would take space from the register fields and the immediate.
Group bitsOPCODE[4:3]A 2-bit pre-decode steers each instruction to the vector unit, memory/AGU, scalar unit or sequencer before the full decode. This comes from v1.0, which based it on the pre-decode / supplement-decode split it cites from Mahmood & Al-Jbaar.—
Register fields3 × 5 bits, typed by opcodeCodes 0–7 name registers; 8 = ZERO for scalar and address fields; 8–15 = window chunks W0–W7 for vector sources. 4 bits would be enough today. 5 keeps v1.0's layout and leaves room for 16 vector registers.v1.0's global 2-bit type tag, which left only 8 of 16 CSRs reachable.
Immediate12 bitsThe largest values are the base address 0x540 (1 344), the loop count 128 and PKOUT's 31. Signed post-increments are ±16. 12 bits covers 0–4 095 unsigned and ±2 047 signed.A wider immediate would squeeze the register fields.
Lanes per PE16L = 64 and B = 128 are multiples of 16. 3 × 16 lanes + 3 scalar multipliers = 51 DSP48E1, which fits the Z7-10's 80. 16 lanes match 16 banks and a 4-level adder tree.32 lanes: 99 DSPs, more than the Z7-10 has. 8 lanes would still meet real time, with roughly twice the MAC instructions; that is a valid smaller option.
PEs3, in lockstepOne per microphone pair, all running the same code. This is the SIMD organisation of Mahmood & Al-Jbaar and the lecture's array processor.One PE reused three times saves 32 DSPs and takes about 3× the cycles (~3 % busy). A valid area option.
Vector registers8 × 16 × 32 bitPhase 3 keeps all 128 error samples resident (128 / 16 = 8 registers); Phase 1 keeps all 64 weights (4). The CRAY-1 also has 8.4 registers: half of e would be reloaded for every column. 16 registers: twice the flip-flops, never used.
Scalar and address registers8 + 8The program uses S0–S1 and A0–A3, A7. Eight of each fit a 3-bit field plus the ZERO code. The CRAY-1 has 8 scalar and 8 address registers too.—
Memory word32 bitsw and g need 32 bits (Q2.30). Samples are stored sign-extended, so every region is addressed the same way.Separate 16-bit sample memory: saves BRAM bits but needs two word sizes in the address generator.
WeightsQ2.30With 16-bit weights the tiny updates get lost: fixed-point τ agrees with float on only 89.1 % of blocks (99.6 % with 32 bits), and accuracy drops from 47.0 % to 43.4 %.Q1.15 weights.
Accumulator48 bits (DSP48E1 P)A Phase 1 sum needs up to 47 bits and a Phase 3 sum up to 39.v1.0 suggested 40 bits, which is too small once weights are 32 bits.
Local memory16 banks × 512 × 32 bit (16 BRAM18) per PEOne bank per lane delivers one aligned row per cycle. Single-word writes (SST) and reads (WSLIDE) use one bank. 1 408 of the 8 192 words are used.One wide RAM gives the row too, but single-word writes then need byte enables across a 512-bit word.
Rings512 words each (X and D)Live data is 191 words (x_full[1…191]) plus room for the next 128-sample block: 319 words, more than 256. 512 is the smallest power of two that fits, and a power of two makes the modulo free (keep the low 9 bits).256-word rings would overwrite live data. v1.0's ping-pong buffers and history copies did not fit.
Ring write offsetsXOFF = L−1, DOFF = L/2XOFF puts x_full[1] (the first sample any product uses) at the block base, so every vector load is aligned. DOFF delays the reference by the center tap while writing, which gives d_delayed for free.Copying x_history and d_history every block, as v1.0 planned.
Window register128 × 16 bitIts length is max(B, L). 16 bits because samples are Q1.15.32-bit entries: twice the flip-flops for nothing.
Instruction memory512 × 32 (one BRAM18)The program is 78 instructions (15 %). One BRAM18 is the smallest unit.—
Loop stack2 levelsThe program uses 1. When B or L exceeds 128, w or e no longer fits in 8 registers, so each VMAC needs its own VLD. The body then outgrows the 31-instruction limit, and the inner loop needs the second level.1 level would block larger parameters.
Control flowno branchesLoop counts and addresses never depend on the data. The cycle count was the same on all 600 simulated blocks.A branch unit and predictor, with nothing to predict.
Hazardsscoreboard (hardware interlocks)The program stays correct if synthesis changes a latency. It costs about 20 small ready-time counters.Scheduling NOPs in the program gives the same cycle count today, but the program would have to change whenever a latency changes.
Clock100 MHzA standard FCLK_CLK0 setting. At 27 µs per block the cluster is busy 1 % of the time, so there is no reason to push it.The real Fmax comes from synthesis.
Number formatfixed pointDSP48E1 slices are integer multipliers. The fixed-point run matches float on 99.6 % of blocks.float32 (v1.0) would need floating-point IP cores in every lane.
